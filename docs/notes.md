## The engine is `bw`

Homebrew's `bitwarden-cli` is 2026.9.1 on 2026-10-07, GPL-3.0-only, and depends on `node`. It installs `bw` at `/opt/homebrew/bin/bw`. It is a node program, so every start of it is node starting: `bw status` on a logged-out CLI took 1.26 s, 1.26 s and 1.47 s here on 2026-10-08, and that is the floor under every one-shot command and under a cold child. Logged in and locked, the same command took 1.31 s, 1.319 s and 1.318 s on 2026-10-10. A child is quicker than a one-shot: `bw serve` answered its first `/status` between 0.30 s and 0.47 s after it was started, six starts, and a child started with a session had answered its first `GET /list/object/items`, a few hundred items, 1.048 s, 1.027 s and 0.684 s after the start. That is finger to first row as far as the engine goes, and it is under D7's 1.5 s. The script's first line names `/opt/homebrew/opt/node/bin/node` outright, so the child needs no `PATH` to find node, and the node on a user's own `PATH` (22, under `~/.local/bin`) is not the one that runs it. Installing the formula brought Homebrew's node to 26.11.0. This app runs it as a separate program and links none of it.

`BITWARDENCLI_APPDATA_DIR` moves the CLI's `data.json`, which is how its help says to keep two accounts apart. This app sets it to `~/Library/Application Support/OriPass/bw/`, so the app's login is its own: a `bw` typed in a terminal without that variable sees a different, logged-out CLI.

`bw config server https://vault.bitwarden.eu` points it at the EU server, and a self-hosted server takes its own URL the same way. It has to be said before the login, not after: with an account present it answers "Logout required before server config update." `https://bitwarden.com`, `bitwarden.com` and `null` all mean the default again, after which `status` shows `serverUrl` as null. It saves an `http` address without complaint and refuses it at the login: "Error: Insecure URL not allowed. All URLs must use HTTPS."

`bw status` prints JSON with `serverUrl`, `lastSync`, `userEmail`, `userId` and `status`, the last one of `unauthenticated`, `locked` or `unlocked`. Logged out it is exactly `{"serverUrl":null,"lastSync":null,"status":"unauthenticated"}`: the two user keys are absent, not null. Locked and unlocked it has all five, `serverUrl` null on Bitwarden's own server, and `lastSync` a string of 24 characters, which is the length of an ISO-8601 time with milliseconds and a Z; the run printed its length and not its characters. Over the socket `GET /status` wraps the same object: `data.object` is `template` and the five keys are under `data.template`.

`bw login [email] [password]` takes `--passwordenv <NAME>` and `--passwordfile <path>` as `unlock` does, `--method <n>` and `--code <code>` for two-step login, `--apikey` (which reads `BW_CLIENTID` and `BW_CLIENTSECRET`), and `--sso`. `bw unlock --raw` prints the session key and nothing else. A good login prints a session key too, in its message and as `raw` under `--response`.

What it says when a login does not go through was run on 2026-10-08, by `scripts/spike-login.py`: the real 2026.9.1 pointed at a server on 127.0.0.1 that refuses every login, with no account and no network (`docs/spikes/login-2026-10.md`). The CLI's sentences below are therefore measured. The server's half is not: the refusals it was fed are what the CLI's own parsing expects, and the two sentences marked *server* are whatever the server sends, passed through. No login that works has been run. That is OP-18's box by hand.

With `--response` every verdict is one line of JSON on standard output, `{"success":false,"message":"…"}`, exit 1. A wrong password: "Invalid master password. Confirm your email is correct and your account was created on <host>." No password in the named variable: "Master password is required." An email with no `@`: "Email address is invalid." A server that is not there: "FetchError: request to <url> failed, reason: …". A wrong API key: "client_id or client_secret is incorrect. Try again."; an organisation's: "Invalid API Key; Organization API Key currently not supported"; none: "client_id is required." An account already here: "You are already logged in as <email>."

A second step depends on whether the CLI may ask. With `BW_NOINTERACTION=true` and one method on the account it answers "Code is required."; with more than one and no `--method`, "Login failed. No provider selected."; with a method the CLI cannot do (a passkey, Duo: `supportsDuo` is false in it), "No providers available for this client." When the one method is email it sends the email before it answers, on every attempt. A wrong code is *server*: "Two-step token is invalid. Try again." was what the spike's server said.

The emailed code for a new device cannot be given without interaction at all. There is no option for it, and told not to ask, the CLI answers "Code is required.", the same words as for a missing two-step code. A wrong one is *server*.

Left free to ask, it needs no terminal. Each question is written on standard error by `inquirer`, with terminal escapes round it, and the answer is a line on standard input, which may be a pipe or a named pipe: "? Two-step login code:", "? New device verification required. Enter OTP sent to login email:", and a list, "? Two-step login method: (Use arrow keys)", whose rows were "Authenticator App" and "Email" above a rule and "Cancel". A YubiKey's row was not seen; its name in the CLI's own strings is "Yubico OTP Security Key". The list wants arrow keys and is not answered here: the child is killed and started again with `--method` (0 authenticator, 1 email, 3 YubiKey). The CLI writes each question again with the answer after it, so a code that was sent is on standard error afterwards, and that stream is never logged. At the end of its input it does not give up. It sits at its question for ever, which is why `LoginChild` kills it.

So the app's login is `bw login <email> --passwordenv OP_MASTER_PASSWORD --response`, with `--method <n>` once a method is chosen, the password in the child's environment, `BW_NOINTERACTION` not set, and the code down a pipe. `--code` is never used: it is an argument. Nothing in 2026.9.1 asks for an API key by itself. The prompt for one after a password ("Additional authentication required.") is still in the source and has no caller, so the API key is for the account whose only second step is one the CLI cannot do, and for whatever the server refuses that this was not able to provoke. An account that signs in through an organisation's SSO would make a CLI that may ask open a browser and wait; this app stops it after two minutes.

`bw delete item <id>` moves an item to the trash, where the server keeps it thirty days; `--permanent` skips the trash and cannot be undone; `bw restore item <id>` brings one back.

A process's arguments can be read by every user on the Mac through `ps`. Its environment can be read only by the same user, with `ps eww`. So a password never goes in an argument. Since OP-66 nothing that opens the vault goes in the serving child's environment either: it has no `BW_SESSION`, and the password reaches it down its connection (D7). The login child is the one left with a password in its environment.

What the environment costs on this side of the hand-off, which is now the login's alone. `Process.environment` takes a `[String: String]`, so the master password handed to the login child is a Swift `String` inside Foundation's `Process`, copied out of the `SecretBytes` by `withBytes` on the way. It lives as long as the `LoginChild`'s `Process` does. A `String` cannot be overwritten, and `Process` has no call that clears one it was given, so the only end to it is the `Process` being released, which `stop()` does by setting `process = nil`. The dictionary built in `LoginChild.start` is a local and is gone when `start` returns, so there is no earlier release to make: the copy in the `Process` is the one that stays. `SecretBytes` covers a secret up to that hand-off and nothing after it, and the memory of a locked app can still hold a string that was a password until the allocator reuses it. The serving child is started with `posix_spawn` and an environment of four names, none of them secret.

## `bw serve`

From `serve.command.ts`: the port defaults to 8087 and the hostname to `localhost`. A hostname that starts `unix://` is a socket file to listen on. `fd+listening://<n>` takes a descriptor that is already listening, `fd+connected://<n>` serves one socket that is already connected, and `all` binds every interface. `--disable-origin-protection` turns off the check of the `Host` and `Origin` headers that is on by default. Nothing in that file sets the socket file's mode, so the directory it sits in is what protects it: make the directory 0700 before the child starts. Socket files shipped in CLI 2025.10.0.

No request carries a credential, and every request has to name a host. With origin protection on, `serve` answers 403 with nine plain bytes and no envelope (the first run counted ten because its `echo` added a newline; the bytes were not printed, and the stand-in sends "Forbidden", the status's own word, which is nine) unless the `Host` header, in lower case, is `localhost:<port>`, `127.0.0.1:<port>`, `[::1]:<port>` or `<this Mac's name>:<port>`. The port is `--port`, or 8087 when that option is not given, and the rule is the same on a socket file, where no port exists. The names without a port pass only when the port is 80 or 443. A request with any `Origin` header is refused 403 too, and one with an empty `Host` is 400. `--hostname all` switches the Host check off, and is every interface over TCP, which is not what this app wants.

This was learnt on 2026-10-10 from the first run of `scripts/spike-bw.sh` against a logged-in 2026.9.1, and then read in the installed CLI's serve command. The script and the app both sent `Host: localhost`, and every request came back 403, `POST /unlock` with a wrong password and with the right one alike: until that day nothing in this app had worked against the real `bw`. The app now sends `Host: localhost:8087` (`ServeClient.host`), passes no `--port` and leaves the protection on. Run on the second sitting that day, on a socket file: `localhost:8087` and `127.0.0.1:8087` 200, `localhost` and `evil.example` 403, no Host 400, and `localhost:8087` with an `Origin` header 403. `[::1]:8087` and the Mac's own name were read and not tried. `Tests/Support/standin-bw.py` refuses by the same rule, so a client that drops the port fails `ServeClientTests`.

A 403 is not a slow start. `BwChild` takes any HTTP answer to its probe as the child being up, and the first call then throws `VaultError.turnedAway` with the status, which the lock screen shows as "The engine turned the request away with HTTP 403 and no reason." If a later `bw` moves the rule again, that sentence is where it shows.

As built (OP-65). `ServeConnection` is the app's end of the pair and `ServeClient` writes HTTP/1.1 over it by hand, with no `Connection` header, so the connection is kept. Requests go one at a time in the order they were made, each after the last one's answer, on a queue of the connection's own, and a request's deadline of sixty seconds starts when its turn comes. Since the end of an answer is no longer the end of the connection, an answer is cut from what has been read by its `Content-Length` or its chunks; one that names neither runs to the end of the connection. A request that is not answered whole, because the deadline passed, the child closed its end or what came was no HTTP, leaves the connection of no use, because an answer that came late would be read as the next request's. The connection is shut there, every request waiting behind it fails at once, the child is told to go, and the store locks with "The engine stopped answering." where a wrong password's sentence would be. A child that closes its connection is only noticed at the next request, or when it exits; nothing watches an idle connection. `ServeClientTests` and `ServeBackendTests` hold all of it against the stand-in, which serves a connected socket and nothing else, so no test makes a socket file. The stand-in closes the connection after its 400 for a request with no Host, which is a guess: what the real one does with the connection then was not read.

`scripts/spike-bw.sh` and `scripts/contract.sh` still start a `bw` of their own on a socket file, `spike.sock` and `contract.sock` under the app's run directory, because `curl` cannot be handed a socketpair. For the length of such a run, by hand, the line is the old one, and both headers say so.

On the Swift side `URLSession` cannot speak over a descriptor it did not open, and `Process` cannot hand a child a descriptor other than the first three. So the child is started with `posix_spawn`: its end of the pair copied to descriptor 3, `/dev/null` on its input and output, a pipe on standard error for the sentence it exits with, and `POSIX_SPAWN_CLOEXEC_DEFAULT`, so that nothing else the app has open reaches it. Both ends are marked close-on-exec as they are made, so no other child of the app inherits either. The app closes its copy of the child's end as soon as the child exists: while that copy was open the connection could never be seen to end, and a `bw` that exited at once with "You are not logged in." was waited on for the whole thirty seconds, which is what the first run of `BwChildTests` showed.

An id in a request line. The line is written by hand, `METHOD path HTTP/1.1`, and until 2026-10-11 an item's, a folder's and an attachment's id went into the path as the engine's answer held it. ## Sessions

From `node-env-secure-storage.service.ts`: what the CLI needs to reopen the vault is kept in `data.json` under keys prefixed `__PROTECTED__`, encrypted with the session key, and the session key is read from `BW_SESSION` in the environment. Without the variable, or with the wrong value, the protected entry decrypts to nothing and the vault is locked.

Every `bw` command is a new process, and the documented way of working is `export BW_SESSION=...` followed by commands. So a `bw` that starts with a valid `BW_SESSION` has the vault open without a password, and `serve` is one more command of the same program. Run on 2026-10-10, three times: a child started with the variable set said `unlocked` at `/status` and answered `GET /list/object/items` with no `POST /unlock` sent, and the same session did it again after each child was killed, which was this app's ordinary lock until OP-66. The app no longer starts a child that way.

The help says `bw lock` and `bw logout` invalidate the session key. That makes two kinds of lock. Killing the child leaves the session good, for whoever has it. `bw`'s own ends it, and only the master password makes another. Until OP-66 the app had the session, sealed, and used the first for every ordinary lock and the second to end one for real. Now it has none and the difference is small: an ordinary lock kills the child, and "Lock and forget" sends `POST /lock` first, so that the session the child made opens nothing afterwards, even for whoever had read it. Run: after `POST /lock`, which answered 200, a new child started with the same session said `locked` and refused the list with "Vault is locked.". The child that was sent `/lock` goes on running. Run on 2026-10-11 on a connected socket, three rounds on one child: `/lock` answered 200 in 0.132 s, 0.014 s and 0.017 s, a list was then HTTP 400, "Vault is locked.", `/status` said `locked` from the same process, and `POST /unlock` on the same connection opened it again in 0.501 s, 0.607 s and 0.606 s, each time with a session the run had not seen before, the first list 0.038 s after. The app does not keep such a child (D18): `ServeBackend.endSession` kills it after the call, and a lock kills it. `bw lock` as a one-shot command was never run, and since OP-66 the app never runs it: with no child serving, `endSession` does nothing, because the session a child made went with that child.

A child needs no session in its environment to be opened. Run on 2026-10-11: started with no `BW_SESSION` and sent the password over the connection, it answered the list, and the session it made was in `data.raw` of the answer and nowhere another process could read ("What another process can see of the child"). The answer is not read for its session. ## A child that outlives its parent

If this app crashed with the vault unlocked, a `bw serve` listening somewhere would keep listening with nobody to lock it. A child on a connected socket cannot: it has one connection, and when the app's end of it closes, because of a lock, a quit, a crash or a `kill -9`, it reads the end of that connection and exits. Run on 2026-10-11, the real `bw` with nothing watching it: it exited by itself with status 0, 2.010 s after the other end closed with the vault open, 2.026 s after with the vault locked by `/lock`, and 1.020 s after for a locked child that had been kept through two idle waits. Why one second and not two that last time was not looked into.

So there is no shell around the child and no watcher beside it, as there were until OP-65: `BwChild` starts `bw` itself. How the app learns that `bw` died on its own: a dispatch source on the pid, which is the kernel saying so, and then `waitpid`. Nothing polls. The app writes `bw`'s pid to `run/child.pid` when it starts it and removes the file when the child is known to be gone, so the run directory holds that file while a child lives and nothing at any other time.

`BwChild.stop` shuts the app's end, sends `SIGTERM`, waits up to two and a half seconds and then sends `SIGKILL`. Shutting the end would be enough for the real one, by the run above, and the card for OP-65 had `stop` do only that and wait. It sends the signal as well because the wait is two seconds in which the vault is still open in a process, and `VaultStore.lock` awaits the stop before it says it is locked, so the lock screen would have come two seconds late. The watcher that is gone sent the same signal the moment its pipe closed, so the real `bw` has been ended this way at every lock since the app first opened that vault. What a lock no longer exercises is the exit by itself, which is left for a crash and a `kill -9`. `BwChildTests` holds each: the stand-in takes two seconds to go when its connection ends, as the real one did, a stop takes under one, a host killed with `kill -9` leaves no child three seconds later, and a stand-in told to ignore both the signal and the closed connection is killed after the wait. A child still there after the kill and a second wait keeps its pid in the file, since the file is all the cleanup below could kill it by. Nothing outlives `SIGKILL` in a test, so that one is a `BwChild` whose signals go nowhere: `stop` returns after both waits, the file is there, and `clearLeftovers` kills the child.

`bw` needs no `PATH` to find node, since its first line names it. The child is given `/opt/homebrew/bin:/usr/bin:/bin` all the same, with `HOME`, `BITWARDENCLI_APPDATA_DIR` and `BW_NOINTERACTION`, and nothing inherited: no signal blocked or ignored, and no descriptor but the four it is handed.

The belt beside the braces, for a child that hangs when its connection ends, which no run has seen: as the app launches over the real vault (`ServeBackend.clearLeftovers`, which a demo and the tour never reach) and before every start, the pid in `child.pid` is killed if its arguments, read with `sysctl`'s `KERN_PROCARGS2`, are still `serve` on `fd+connected://3`, or on the socket file a build from before OP-65 used, and a `serve.sock` that build left is removed. A pid that has been handed to somebody else since is left alone. The arguments no longer name the run directory, so two copies of the app running at once would each take the other's child for a leftover; the old check had the same hole, since both served the same path. All of this is asserted by `BwChildTests` and `ServeBackendTests` with a stand-in script in place of `bw`, except the one line in `AppDelegate` that calls it at launch, which no hosted test reaches; the real `bw` under the app's own `BwChild` was seen on 2026-10-11, by hand: with that vault open the child was `bw serve --hostname fd+connected://3` and the run directory held `child.pid` alone.

`LoginChild`, the one `bw` that may ask a question, is still behind a shell that kills it when the app lets go. It serves nothing and is not this section's.

## A finger without a provisioning profile

A keychain item protected by a `SecAccessControl` with biometry lives in the data protection keychain. A Mac app reaches that keychain only with an application identifier or a keychain access group in its entitlements, and those are authorised by a provisioning profile; without one the call fails with `errSecMissingEntitlement`, -34018. Apple's table gives Keychain sharing to a free account, so a profile could carry it, but OriNotch's D21 found free profiles last seven days on the phone, and an app whose profile has lapsed does not launch. OriNotch ships with no profile at all. So does this app.

CryptoKit's `SecureEnclave.P256.KeyAgreement.PrivateKey(accessControl:)` makes a key inside the enclave and hands back `dataRepresentation`, a blob only this Mac's enclave can use, which the app keeps in a file. No entitlement is needed. Run on 2026-10-08: `scripts/spike-seal.swift`, a plain script under `swift`, made the key, sealed thirty-two bytes and unsealed them in a second process after one Touch ID sheet; the signed Debug bundle did the same behind `OP_DEMO=seal` and `OP_DEMO=unseal`, and `codesign -d --entitlements -` on that bundle printed nothing. Since OP-35 the bundle carries one entitlement, `com.apple.security.automation.apple-events`, for the tab of the browser in front ("What is in front"). On 2026-10-09 the bundle signed with it made an enclave key and sealed to it behind `OP_DEMO=seal`. *check*, by hand and OP-35's sixth box: that `OP_DEMO=unseal` from that bundle still raises the sheet and prints "match". If it does not, the entitlement goes. Making the key and sealing to it ask for nothing. Only the unseal asks, and with `interactionNotAllowed` set on the context it fails with `LAError` -1004, "User interaction is required.", so the finger is the enclave's demand and not this app's manners.

Sealing to that key is HPKE: CryptoKit takes the enclave key's public half as an `HPKE.Sender`'s recipient and the enclave key itself as an `HPKE.Recipient`'s private key, with `P256_SHA256_AES_GCM_256`. Three things are kept: the key's blob (569 bytes), the encapsulated key (65) and the box (the secret plus a 16-byte tag). Unsealing asks the enclave for the key agreement, and the enclave asks for the finger. The access control is `privateKeyUsage` with `biometryCurrentSet`, so enrolling a new fingerprint kills the key, which is the point.

The blob survives the app being rebuilt and signed again: sealed by a bundle with one CDHash, unsealed by the next build with another. The enclave key is tied to this Mac and to the enrolled fingerprints and to nothing about the code. That has a second edge. Any program running as the user that reads the two files can ask the enclave to unseal them, and what stands in its way is the Touch ID sheet, which names the asking process's reason and not its identity. It is D5's line again.

The sheet's reason is `LAContext.localizedReason` on the context handed to the key. Two failures were not watched, because they need a person and not a session: the sheet cancelled, and the lid shut with an outside keyboard so that there is no sensor. The first has been seen since: on the installed app, on a personal vault, on 2026-10-10 and 11, he cancelled the sheet, the password field was there, and the log gave `LAError` -2, which the headers call `userCancel`. The second is still *check*, by hand. `Door.askForFinger` treats any error from the unseal as "show the password field" whichever error it is, and logs the error's code, so the first cancelled sheet and the first shut lid leave their numbers in the log.

What `PasswordSeal` keeps: two files under `seal/`, mode 0600 in a directory of mode 0700. `key` is the enclave key's blob. `password` is JSON with five members: `form`, which is 2, `made`, the second the password was sealed in, as a whole number since 1970, `encapsulated` and `box` in base64, and `fingers`, a mark of the fingerprints enrolled at that second. `made` and `fingers` are handed to HPKE together as the data it authenticates, on the way in and on the way out, so a date or a mark edited in the file, or a mark taken out of it, gives a seal that does not open. The first build that sealed a password (940534f) bound the date alone and wrote no `form`. A file without the 2 is not read as a seal, and a seal made over a directory that holds one deletes it with its key, unopened, so the password is typed once and sealed again. That is held against the fake; nothing could hold it against the real enclave without a finger. `HPKE.Sender.seal` takes an `UnsafeRawBufferPointer`, so the password goes from its `SecretBytes` into the box without a `Data` in between. On the way out CryptoKit returns a `Data`, which is copied into a `SecretBytes` and zeroed as far as a `Data` can be. Run on 2026-10-11 against the real enclave from the hosted tests, as on 2026-10-08 when the box held a session: neither file holds the sealed bytes as they are or under base64, at any of the three places in a run of three bytes they could begin. Until that day the second file was `session` and its box held the session key. ## Secure input

### When a list comes back short

Found in use on 2026-11-01: items left the window by themselves, more often than before, and Sync Now brought them back. Two things were found: an answer of the engine's that the app believed, whose cause is read and not run, and a race of the app's own, which is run. Neither is a view's: `SyncTests.testTheListIsWhatTheStoreHoldsAfterEveryKindOfChange` holds `Panes.list` to the store after every kind of change, a filter, a card and a search among them, and it passed before anything here was changed, so the card's second suspect is cleared.

The app believed every list it was handed. `VaultStore.sync` put whatever the two reads brought in place of what it held, with nothing to say a read was wrong, so one short answer emptied the window and the next read filled it. That part is run: over the stand-in, with `emptyAfterSync` and with `bw`'s own envelope and a 200, the test that goes red on the old code ended with no items in the store.

Why `bw` would answer so is read and not run. In 2026.9.1's source (`cipher.service.ts`, from `bw.js.map`) `getAllDecryptedUsingSdk` wraps the SDK's decryption in a `try` whose `catch` is `return []`, with the comment "Return empty array on error to maintain existing behavior", and `setDecryptedCipherCache` refuses to cache an empty list because "sometimes we might prematurely decrypt the vault". So a decryption that throws is no rows and a 200, and the next read decrypts again and has them all, which is the one shape that fits Sync Now curing it: a list short by a few is cached, and an unforced sync that finds nothing new clears no cache. `default-sdk.service.ts` is where it can throw. Its client is built again whenever a key or the account's state re-emits, the old one is marked for disposal as that starts, and a comment there names the race during an unlock; a client unused for a second is dropped too. `/sync` runs `syncProfile`, which sets those keys, only when the server's revision has moved past `lastSync`, and `cipherService.replace` clears the decrypted list only then. Nothing changed means nothing happens, so the more a day writes, from the Mac or the phone, the more real syncs there are for a read to land behind. That would be why it came more often in a day of passkeys and edits, and it is the only reason for it found. No read of the real `bw` has been seen short, and the app's `POST /sync` and its lists were never asked in that order by a spike. `scripts/spike-sync.py`, by hand, does exactly that, on a note of its own, and prints counts.

Whatever the engine does, a read now has to earn taking something away. `VaultStore.missing` is what is held and in neither list. An item that went from one list to the other has its reason in the read and lands at once; anything else is doubted, nothing is merged, and two seconds later (`VaultStore.secondRead`) the lists are read again. The second read is believed when all it misses was missed by the first too, so a delete on another device arrives two seconds later. When it misses something the first had, the two disagree, nothing changes and the next sync asks. A read that takes nothing away is merged at once, as before, so a held-off read moves no revision and the selection and the scroll stay where they were. Two empty reads two seconds apart would still empty the window: the card asks for two, and a vault emptied elsewhere has to be able to land.

An unlock has nothing held to doubt a list against, and the source's own comment places the race there, so `load` reads again after the same two seconds when the items come back empty. A vault that really is empty costs that wait at each unlock. A list short but not empty at an unlock is not caught, and stands until a sync brings the rest.

The race is the app's own. A list read before a change was answered has not heard of the change. With a new item made between `/list/object/items` and the merge, the item left the store; a restored one went back to the trash; a favourite was undone. Each came back at the next sync, which is the same symptom for one item at a time. A sync's reads now wait for what is being written (`settle`, five seconds at most) and start again when a change was sent during them (`listsNoChangeLandedAmong`), and every write goes through `writing`, so this holds for all of them. An unlock does not wait: a change left over from the last opening is filed nowhere (`apply`), and it has nothing to take back.

Each read leaves one line in the unified log at `notice`, which is kept on disk where a `debug` line is not. It holds counts and no id: which read it was (`unlock`, `sync` or `second`), the items, the trash and the folders it brought, what was held, and how many are missing. ## How strong

Read on GitHub and run on this Mac on 2026-10-08.

Bitwarden's apps score a password with zxcvbn. Four Swift ports of it were read through GitHub's API and none was vendored. `DeVitoC/zxcvbn-swift` (MIT, 7 stars, last touched in March 2024) is 62 KB of Swift and a 1.26 MB `frequency-lists.json`. `quickbit/zxcvbn.swift` (MIT, 1 star) is 1.33 MB, of which 1.28 MB is one Swift file of the same lists. `kokluch/zxcvbn-swift` (MIT, one commit, August 2026) is 4.97 MB with 4.86 MB of word lists and asks for Swift tools 6.2. `naltinbas/Keenward` (MIT) is 2.17 MB of Swift and is not zxcvbn. The card asked for small, and in every one of them the estimator is a few tens of kilobytes and the rest is about a hundred thousand words. The first and the third also read their lists through `Bundle.module`, which a file copied into an app target does not have, so neither could have gone in at a pinned commit untouched.

So `Strength` is this repo's own, in `Sources/Strength/`, and its level is an estimate. `Guesswork` is zxcvbn's method written from its description: every stretch of the password that is a word, a run along the keyboard, a repeat, a sequence or a date is given the number of tries that kind of thing takes, the stretches between are ten tries a character, and the answer is the cheapest way of covering the whole password, where a way made of *n* pieces costs *n* factorial times its pieces multiplied plus 10,000 to the power of *n* less one. The levels are cut where zxcvbn cuts its five scores, at a thousand, a million, a hundred million and ten thousand million guesses. The keyboard figures, 47 keys and 4.6 neighbours, are its figures for the American layout, used for the Turkish Q as well.

Where it will disagree with Bitwarden's apps. `Words` holds about nine hundred words, written here: the stems of the passwords every leak has, the commonest English and Turkish words, and given names in both. zxcvbn holds about a hundred thousand, English only. A word this list lacks is counted as letters nobody could guess, so a password built on an uncommon English word comes out a level or more higher here than there, and one built on a Turkish word or name comes out lower here, which is the truer of the two for this account. Nothing of the item is read beside the password: zxcvbn lets a caller hand in the username and the site's name as words to look for, and this does not yet. Only the first 64 characters are read.

What the four passwords the card names came to, with dates counted from 2026: `password` Guessable, `qwerty123` Weak, `Meric2026!` Fair, twenty random characters Strong. `Meric2026!` is Fair and not Good because `meric` is in the names: a name and then five characters of anything is about fifty million guesses.

What scoring costs. The store scores every password that has no level behind each load and each sync, in one detached task, and publishes once. Two thousand passwords, three in four of them 27 random characters, took between 0.56 and 1.16 seconds in a Debug build across three runs while another project was building. In that time the main thread, kept turning by the test, did at most 0.44 ms of work in one turn by its own processor time. By the clock it was once 30 ms away in a run of the whole suite and 1 to 3.5 ms in the others; the clock counts the other build's share of the processor, which is why the test asserts on processor time. The app's Release build was not timed; the two files compiled alone with `-O` scored 2,000 passwords of about thirty characters in 0.10 s. No window was on screen.
