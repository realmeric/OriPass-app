## Signing in

Prelogin is `POST {identity}/accounts/prelogin/password` with `{"email": …}`; the older `accounts/prelogin` answers the same and the server marks it obsolete. The answer has `kdf`, `kdfIterations`, `kdfMemory` and `kdfParallelism`, and newer servers add `kdfSettings` and `salt`, the salt being the email for now. `kdf` is 0 for PBKDF2-SHA256 and 1 for Argon2id.

The token is `POST {identity}/connect/token`, form-encoded: `scope=api offline_access`, `client_id=mobile`, `deviceIdentifier` (a UUID kept for the install), `deviceName`, `deviceType` (1 is iOS), and for a password `grant_type=password`, `username`, `password` (the server hash, below). A second step adds `twoFactorToken`, `twoFactorProvider` (0 authenticator, 1 email) and `twoFactorRemember`. A new-device code adds `newdeviceotp`; the server reads it as `NewDeviceOtp`, case not mattering. Bitwarden's iPhone app sends, on every request, `Bitwarden-Client-Name: mobile`, `Bitwarden-Client-Version`, `Device-Type: 1` and a `User-Agent`.

A 400 with `TwoFactorProviders2` in it asks for a second step from the providers named as its keys. A 400 whose `error` is `device_error` asks for the emailed new-device code, and `POST {api}/accounts/resend-new-device-otp` with the email and the server hash sends another. The new-device code is not asked of an account with two-step login, one signed in by API key, or one under a day old (Bitwarden's help page "New Device Login Protection").

The token's answer has `access_token`, `expires_in`, `refresh_token`, `Key` (the user key under the master key), `PrivateKey`, the KDF again, and `UserDecryptionOptions`. A refresh is `grant_type=refresh_token` with `client_id` and `refresh_token`.

## The keys

The master key is PBKDF2-SHA256 over the password with the email as salt, or Argon2id with the SHA-256 of the email as salt and the memory in MiB; either way the email is trimmed and in lower case first (`bitwarden-crypto`, `kdf.rs`). The server is sent one more round of PBKDF2 over the master key, salted with the password, in base64. The master key is stretched by HKDF's expand step alone, with SHA-256, info "enc" and then "mac", into a 64-byte key that opens the user key: a type 2 string, or type 0 for very old accounts, which the master key opens directly with no MAC. The user key is 64 bytes for every account this app reads; an account on the newer format has a COSE key there instead (I8).

`EncString` types: 0 AES-256-CBC, 2 AES-256-CBC with HMAC-SHA256 over the IV and the ciphertext, 3 and 4 RSA-2048 with OAEP over SHA-256 and SHA-1, 5 and 6 the same with an HMAC beside them, 7 `Cose_Encrypt0`. A string with no "N." prefix is type 0 with two parts (`enc_string/mod.rs`). The account's private key is PKCS#8 DER in a type 2 string under the user key; an organisation's key comes as type 4 under the account's public key.

## What Bitwarden's CLI wanted of the stand-in

Run on 2026-10-26 with Homebrew's `bw` 2026.9.1 against `Phone/scripts/standin.py` (PH-4). It refuses any server address that is not https, so the stand-in has `--tls` and `bw` is given its certificate through `NODE_EXTRA_CA_CERTS`. It asks `GET /api/config` first, then prelogin at `accounts/prelogin/password`. It will not finish a sign-in without `AccountKeys` in the token's answer, `{publicKeyEncryptionKeyPair: {wrappedPrivateKey, publicKey}, signatureKeyPair: null, securityState: null}` for an account on the older format: "Account cryptographic state is required". The same object is `profile.accountKeys` in a sync, so the private key is read from there first and from `profile.privateKey` when it is missing. After its first sync it writes to the account: `POST /api/accounts/key-management/user-key-id`, a migration of its own ("key id backfill"), which the phone never sends. Then `GET /api/accounts/revision-date` around each sync.

## Argon2id

Written here over BLAKE2b and held to RFC 9106 5.3, to `bitwarden-crypto`'s two Argon2id vectors, and to `openssl kdf … ARGON2ID` at Bitwarden's defaults. At those defaults (64 MiB, 3 iterations, 4 lanes) it took 0.061 s on the iOS 26.5 simulator on this Mac's M5, optimised, the four lanes on four threads, and 4.1 s unoptimised, which is why the phone builds with `-O` in Debug too. A phone is slower than an M5; PH-13 measures it there.

## AutoFill

`ASCredentialProviderViewController` (iPhoneOS 27.1 SDK): `prepareCredentialList(for:requestParameters:)` for the list, `provideCredentialWithoutUserInteraction(for: ASCredentialRequest)` for a suggestion picked above the keyboard, with "your extension's view controller is not present on the screen. Do not attempt or expect to show any user interface", and `ASExtensionError.userInteractionRequired` to be asked again through `prepareInterfaceToProvideCredential(for:)`, which can show its view. `prepareOneTimeCodeCredentialList(for:)` since iOS 18. `prepareInterfaceForExtensionConfiguration` is called when the provider is switched on, if `ShowsConfigurationUI` is set. iOS 26.2 adds `performSavePasswordRequestWithoutUserInteractionIfPossible`, `prepareInterfaceForSavePasswordRequest`, `performGeneratePasswordsRequestWithoutUserInteraction` and `prepareInterfaceForGeneratePasswordsRequest`, behind `SupportsSavePasswordCredentials` and the generate capability in `ASCredentialProviderExtensionCapabilities`. `ASSettingsHelper.requestToTurnOnCredentialProviderExtension` (iOS 18) asks the person to switch the app on, in iOS's own words.

The identity store, `ASCredentialIdentityStore.shared`, is what the keyboard reads without starting the extension. Bitwarden's iPhone app replaces it only while its vault is unlocked and the app is in front, because `replaceCredentialIdentities` from the background throws `ASCredentialIdentityStoreErrorDomain` code 0 (`AutofillCredentialService.syncIdentities`, its own comment). It writes one-time-code identities only for an account with Premium.

What the simulator showed (iOS 26.5, 2026-10-26, PH-8). An identity whose service is the address `http://localhost:8099/login` with type URL brought nothing to Safari's keyboard on that page; the same login under the host `localhost` with type domain did, while the vault was locked. Safari on iOS 26 does not always offer it above the keyboard: with one login for the page it put up a sheet of its own, "Sign in to "localhost" with your password for "kanarya-user-1" saved in "OriPass"?" with a Face ID mark and "Fill Password", before any field was typed into. AutoFill is switched on per provider in Settings › General › AutoFill & Passwords, under "AutoFill from:". The simulator's software keyboard shows on a headless device, so the UI tests see what a phone would.

How a fill from that sheet went (PH-9, the same simulator). A tap on "Fill Password" calls `provideCredentialWithoutUserInteraction` first; the extension cancels with `userInteractionRequired`; iOS then presents the extension as a sheet and calls `prepareInterfaceToProvideCredential`, and the view was on screen 575 to 585 ms after that call in five runs. Face ID asked before the view is on screen fails at once (LAError, not interactive), so the extension asks in `viewDidAppear`. iOS's own sheet asks for no face of its own: the one Face ID the person sees is the extension's. From the face to `completeRequest` took 0.1 to 0.2 ms, one item decrypted. Then iOS fills both fields and submits the form: the sheet is "Sign In", and the stand-in's page was posted with the login's username and password. The completion handler of `completeRequest` is called off the main thread, and a closure that Swift 6 takes for the main actor's crashes the extension there.

`LAContext.domainState.biometry.stateHash` is the app's own: the extension read another mark than the app for the same enrolled face, so each keeps and compares its own (`FaceKey.marked`). A UI test run with `test-without-building` does not put a newer build on the simulator; `Phone/scripts/install-built.sh` does, and an AutoFill run that skips it tests the last extension installed. The extension's `Logger` lines did not reach `log show` on the simulator while the app's did; a Debug build writes `trace.log` in the App Group instead (`Trace`).

Turning it on (PH-11). `ASSettingsHelper.requestToTurnOnCredentialProviderExtension` put up iOS's own question on the simulator, "Turn on AutoFill from "OriPass"?", with "When AutoFill is enabled, credentials from "OriPass" will be suggested for filling in apps. You can change this later in Settings." and "Not Now" and "Turn On", and answered true after "Turn On". It did not call the extension's configuration; the app writes the store itself on a yes. Switching the provider on in Settings does call `prepareInterfaceForExtensionConfiguration`, with the extension's view on screen 66 ms later, and a face there let it fill the store before anything was opened.

Codes (PH-12). A field marked `one-time-code` on the stand-in's site brought "verification code for this website — OriPass" and the login's name above a number pad; a tap called the extension with a request of type 3 (`.oneTimeCode`), and after `completeOneTimeCodeRequest` iOS put the code in and submitted the form, and the stand-in found it to be the login's code at that moment. Passkeys are answered the same way, with an assertion signed here (`PasskeyAssertion`): flags 0x1D (present, verified, eligible for backup, backed up) and the counter as it was kept, which is 0 for Bitwarden's passkeys and read by a relying party as no counter. The fixture's passkey is for a site that is not there; what first ran on a page is PH-29's, below.

Making a passkey (PH-29, iOS 26.5, 2026-10-30). The simulator's Safari takes WebAuthn on `http://localhost:8099` with the relying party `localhost`, so `/passkey` on the stand-in runs the whole of it. `navigator.credentials.create` put up iOS's sheet, "Save a passkey?", with "Save in OriPass" ticked over "Save in Passwords" and an "Add Passkey" button. The sheet is its own app, `com.apple.AuthenticationServicesUI`, not Safari; its button is an element marked `ASAuthorizationControllerContinueButton`, whose label is on a static text, and the extension's view is reached through that app too. A tap called `prepareInterface(forPasskeyRegistration:)` with the relying party, the username and the user handle in the request and no display names, and the view was on screen 630 to 760 ms later, with the face asked there. The Sign In sheet then read `Sign in to "localhost" with your passkey for "kanarya-user-7" saved in "OriPass"?` from the identity store, written before the answer went back, and "Use Passkey" called `provideCredentialWithoutUserInteraction`, the interface after `userInteractionRequired`, and the assertion. `excludeCredentials` holding a passkey in the vault reaches the extension in `excludedCredentials`, and `ASExtensionError.matchedExcludedCredential` comes to the page as `InvalidStateError`. A tap on the page in the second or so after a sheet goes lands on nothing, and that app's tree still answers for the sheet that went, so a UI test waits by the clock there.

The entry is what Bitwarden's apps write: `credentialId` a GUID, `keyValue` the PKCS#8 key in base64url, `keyType` `public-key`, `keyAlgorithm` `ECDSA`, `keyCurve` `P-256`, `counter` `0`, `discoverable` `true`, each encrypted, and `creationDate` in the clear. Bitwarden's CLI 2026.9.1 read it on the stand-in, and `openssl` took its key as the half of the public key the page was handed. The AAGUID is sixteen zeros, the attestation format is `none`, and the flags are the assertion's and 0x40.

Syncing in the background (PH-17). `BGTaskScheduler.submit` refuses on the simulator with `BGTaskSchedulerErrorDomain` 1, unavailable, so no background refresh can be fired there, from lldb or otherwise ("No task request with identifier com.meric.oripass.ios.sync has been scheduled"). What the task runs is `BackgroundSync.run`, held by `SyncTests`; on a phone iOS decides when it runs. The app also syncs when it comes to the front and the last sync is a minute old, asking `accounts/revision-date` first and downloading only when it moved.

`ASCredentialIdentityStore.credentialIdentities(forService:credentialIdentityTypes:)` returned nothing to the app on the simulator, for every service and for none, right after a `replaceCredentialIdentities` that succeeded and while Safari offered those very identities. Whether the store holds something is shown in Safari, not read back.

Signing up (PH-22, iOS 26.5). On a field marked `new-password` with `passwordrules`, Safari put up "Use Strong Password?" with "Save in OriPass" (a menu with OriPass's icon) and "Fill Strong Password". A tap called `performWithoutUserInteraction(generatePasswordsRequest:)` with the field's rules, filled what the extension made, and at once asked to save it: `performWithoutUserInteractionIfPossible(savePasswordRequest:)` with event 2 (a generated password filled), and after `userInteractionRequired` the save interface, on screen 700 ms later. Under a face the extension made the login through the API, and the page was submitted with a password of the 24 characters its rules asked for.

A fill in a grace (PH-25). With a copy of the key kept without Face ID, the extension answered `provideCredentialWithoutUserInteraction` at once, 16 ms after it was asked, and its view never came up. iOS then asked for a face of its own over its sheet before it filled: with no match sent to the simulator the fill waited there, and with one it filled and submitted in five seconds of test time. So iOS checks the person itself when a provider answers without an interface, where in PH-9, through the interface, the only face was the extension's. That check is iOS's device-owner check, which falls back to the passcode.

The extension's memory: about 120 MB, by Bitwarden's forum and their staff's answers there; Apple publishes no figure. Their app warns that an Argon2id unlock may fail in the extension and recommends biometrics, which skips the KDF. Measured here on the simulator (PH-10): the extension's list at 35 MB before the master password, Argon2id at Bitwarden's defaults run inside it in about 50 ms, and `ledger_phys_footprint_peak` at 99 MB after it, which leaves about 20 MB under the forum's figure. A phone's own number is PH-13's.

The list (PH-10). The keyboard's key is "Passwords" in an app and "Password Auto-fill" above Safari's keyboard, and a tap asks which provider, "OriPass" or "Passwords", before `prepareCredentialList` is called. An app with no associated domain is asked for with no service identifiers at all. With the sheet closed, Safari put the login above its keyboard as "password for this website — OriPass" and the username.

The AutoFill credential provider is a paid-programme capability on iOS: Apple's "Supported capabilities (iOS)" table gives it, associated domains and push to the Apple Developer Program and not to a free account, and gives app groups, keychain sharing and background modes to both.

## A real vault in counts

A personal account read on a phone, About This Vault, relayed as counts and never a value: every encrypted string was type 2 and none type 7, and the master key was made by PBKDF2-SHA256 at 600,000 iterations, about a tenth of a second from a face accepted to the vault open. So the phone read all of it with the types it has, never ran Argon2id for that account, and had no organisation's key to open.
