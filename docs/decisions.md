# Decisions

The code and the notes cite these by number. Each is settled; changing one is a change to this file first.

- D1, the name. Display name, target, scheme, module and product all `OriPass`, bundle id `com.meric.oripass`, demo variable `OP_DEMO`. Nothing in the name, the icon or any string says 1Password or Bitwarden, except where the app has to name the tool it needs.
- D2, the repository. The fixtures are invented and the demo vault is canaries, because a password manager's repository is a bad place to learn that a real value slipped in.
- D3, the floor. macOS 27.0, arm64 only, Swift 5 language mode under the 6.4 compiler. No dependency beyond Apple's frameworks. Two things are vendored as data: the Public Suffix List and a word list for the strength estimate.
- D4, who holds the vault. Bitwarden's server, and on the Mac the official CLI, Homebrew's `bw`, not bundled. `bw` logs in, syncs, decrypts and writes; this app never derives a key, decrypts a cipher string or keeps a token. Its state lives under `~/Library/Application Support/OriPass/bw/` through `BITWARDENCLI_APPDATA_DIR`, so a `bw` in a terminal neither sees it nor disturbs it. The alternative, Bitwarden's SDK inside this process, is not for public use and would make login and sync this repository's to write.
- D5, how the CLI is spoken to, and what that leaves. Over one connected socket handed to the child at birth, `bw serve --hostname fd+connected://<n>`, the app keeping one end of a socketpair. No socket file is made and nothing listens. What it gives up: the child is Homebrew's node, not a hardened process, so a debugger running as the user can read the decrypted vault while it is open ("What it is not" in the README).
- D6, what unlocked means. While unlocked, every item is decrypted in memory in one `VaultStore`; views read the store and never the engine. Lock empties the store, kills the child, clears the pasteboard if what is on it is this app's, and swaps every window for the lock screen. Nothing decrypted is written anywhere: no cache, no search index on disk, no window restoration, no log line that carries a value. `make canary` is how this is known.
- D7, the finger. What is sealed to a Secure Enclave key is the master password, under `biometryCurrentSet`, in a file under the app's Application Support, for fourteen days. The child is started with no `BW_SESSION`; a finger unseals the password, which goes to the child as `POST /unlock` over D5's connection and is wiped.
- D8, the look. Layout, order, proportion, behaviour and keyboard as `docs/look.md` describes, in the manner of 1Password for Mac, with every glyph, icon, colour and sentence this app's own.
- D9, a vault is a folder. The sidebar's vaults are the account's folders, and items in no folder sit in a first row called Personal. An organisation's collections are shown as vaults items cannot be dragged into.
- D10, no tags. Bitwarden has none. A custom field read as tags would show up as a field in every other client, so the Tags section is not drawn.
- D11, five categories. Login, Secure Note, Credit Card, Identity and SSH Key. A type the app does not know is listed with a plain mark, shown field by field, and never written back.
- D12, one-time codes. Computed here, RFC 6238 over `login.totp` with CryptoKit's HMAC. Bitwarden sells codes as part of Premium; the README says so.
- D13, Password Health is arithmetic done here. Reused, weak, unsecured and expiring are computed from the store and ask nobody. Breached passwords (Have I Been Pwned, by range) and the two-factor list (2FA Directory) are off until switched on, because they are the only requests the app makes that the user did not make by clicking.
- D14, what leaves the Mac. The child speaks to Bitwarden. The app fetches site icons from Bitwarden's icon server, with a switch to turn that off, and D13's two requests when on. No analytics, no update check, no crash reporter.
- D15, the pasteboard. A copy carries `org.nspasteboard.ConcealedType`, stays off Universal Clipboard, and is cleared after ninety seconds if the change count is still the one the app left. Filling never goes through the pasteboard.
- D16, the keys. Quick Access on ⌥⌘\, Lock on ⇧⌘L, fill on ⌘\, and inside the window the table in `docs/look.md`. In Quick Access, Return copies the password and closes, ⇧Return types the login into the app in front, and → opens the actions.
- D17, filling. In Safari and Orion the app's own extension fills, by a row chosen on the page. The system's AutoFill takes a credential provider, which needs the paid developer programme. Everywhere else the app types the username, a Tab and the password as key events into the app that was in front, which needs Accessibility.
- D18, the budget. Hot key to the panel on screen under 100 ms, the panel built at launch and only shown. A keystroke to its results inside one frame at 2,000 items, held by a test. Finger to first row: what the child takes, and nothing of this app's own on top.
- D19, scope. What is built is the app the README describes.
- D20, what it never does. It does not create accounts, change the master password, set up two-step login, import or export; the web vault does those. It writes no key derivation, cipher or token store, and does not talk to Bitwarden's API itself while the engine is the CLI.
- D21, a pass. The lock no longer means no key is in memory: a pass given with a finger keeps SSH keys' private halves in memory, on no disk, for at most twenty-four hours, through every lock but Lock and Forget. Every other request still needs a finger, and what was signed is reported afterwards.
- D22, a pass is for a whole app. A pass covers one app, by its code signature, and everything it starts, with every SSH key in the vault: logins on a bound session to a host in `known_hosts`, and git commits and tags. Everything else, any other app and anything forwarded, still goes to the card.
