# `bw serve` on a connected socket, October 2026

`bitwarden-cli` 2026.9.1 from Homebrew, macOS 27.0.1. Run on 2026-10-11 at 04:54 by hand, logged in, with `scripts/spike-fd.py`, to the end. It was the script's first meeting with the real `bw`, and no step of it had to be run twice. The report is `docs/spikes/fd-run.txt`, 108 lines, which git ignores. He does not read the reports. The session guiding him read this one at his request and found no value in it, and the session that wrote this page read every line again: no name, no address, no username, no secret and no line that begins `WITHHELD`. The strings in it are lengths, the state word `locked`, header names and two of the CLI's own sentences. Nothing below is a value.

Every child was started as `bw serve --hostname fd+connected://3`, descriptor 3 being one end of a socketpair whose other end the script kept, with no `BW_SESSION` in the environment it was given. No socket file was made and nothing was written to the vault. The letters are the script's.

## a. Does such a child start

It does. Three runs, each asked `GET /status` with `Host: localhost:8087`, each answered HTTP 200 and `locked`: 0.247 s, 0.298 s and 0.293 s from the spawn to the answer. The shape of `/status` is the one a socket file gave: `data.object` "template", and under `data.template` `lastSync` (24 characters), `serverUrl` (null), `status`, `userEmail` and `userId`.

## b. Does the one connection hold

It held for the whole life of every child.

| What | Answer |
| --- | --- |
| a second request at once | HTTP 200 in 0.002 s |
| twenty in a row | 20 answered: fastest 0.001 s, median 0.002 s, slowest 0.002 s |
| after 10 s idle | HTTP 200 in 0.022 s, the same connection |
| after 60 s idle | HTTP 200 in 0.017 s, the same connection |
| answers that said `Connection: close` | 0 |
| `Keep-Alive` headers sent | none |

The two idle waits were on the locked child that was left at the end. An answer's headers were `connection`, `content-length`, `content-type` and `date`, and no others. The first request after an idle wait took about ten times as long as one in a row, which is still 0.02 s.

## g. A wrong password, and a Host with no port

`POST /unlock` with a wrong password: HTTP 400 in 0.211 s, "Cryptography error, The decryption operation failed", and `/status` after it answered 200 and `locked`, so the child goes on. `GET /status` with `Host: localhost`: HTTP 403 with nine bytes, and the connection was still open after the refusal. That was the only wrong Host tried on this transport.

## e. Lock, and open again without a restart

Three rounds on one child and one connection. `POST /lock` answered HTTP 200 in 0.132 s, 0.014 s and 0.017 s, with `data` of `object` "message", `title` (21 characters), a null `message` and `noColor`. A list from the locked child was HTTP 400, "Vault is locked.", each time. `/status` said `locked` and came from the same process each time: the child sent `/lock` goes on running.

`POST /unlock` on the same connection then answered HTTP 200 in 0.501 s, 0.607 s and 0.606 s, each with a session of 88 characters that the run had not seen before, and the first list after it took 0.038 s, 0.039 s and 0.038 s. So a locked child that is kept has the list back in 0.539 s, 0.646 s and 0.644 s, where a cold one takes 1.22 to 1.24 s.

The locked child from outside, after the first round: the table under c again, line for line. The name `BW_SESSION` nowhere, the session it had made and the master password in none of `ps eww`, the arguments and `kern.procargs2` (724 bytes), the same 114 descriptors of the same kinds, one unix socket with no path, no listener, nothing under the run directory, no file open under `bw`'s folder. Resident memory was 255 MB, so the lock gives none of it back. What the process holds in that memory while locked cannot be seen from outside, and the run says nothing of it.
