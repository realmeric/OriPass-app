# OriPass

A native Mac client for a Bitwarden account, with a three-pane window in the manner of 1Password for Mac: a lock screen that opens with a finger, Quick Access on a key from anywhere, a mark in the menu bar, an editor, a generator, Password Health, and a login typed into whatever app is in front. Swift, SwiftUI over AppKit windows, XcodeGen, macOS 27, arm64. Bitwarden's server keeps the vault and Bitwarden's own command line client, `bw`, does every login, sync, decryption and write, run by this app as a child process and spoken to over one connected socket the child is born holding. Every line is this repo's own. Bitwarden's clients (GPL-3) are read for facts and never typed from; `docs/look.md` is the reference for layout, order and proportion, surface by surface, and no artwork, name or sentence of 1Password's is used.

The decisions in `docs/decisions.md` (D1 to D22, cited across the code) are settled; changing one is a change to that file first. Scope is the change at hand: anything else noticed is a note, not an edit. Two checks belong to every change that draws or holds anything: nothing leaks (D6, `make canary`) and the look matches `docs/look.md` (D8, in `make shots`).

## Gate

While a change is worked, run the test classes it touches and no others: `xcodebuild test -only-testing:OriPassTests/<Class>`, with the flags `make test` gives it. The whole gate runs once, last, over a run of changes, before `make install` or a push, and a failure there reruns only what failed. A change to a surface adds `SpokenTests`, `ContrastTests` and `DesignLiteralTests` to its classes.

`make test` is the definition of done, on an unlocked screen, and `make canary` is its second half: `xcodegen generate`, then `xcodebuild test` on the Debug scheme, then `scripts/canary.sh`, which unlocks the demo vault, uses it, locks, and fails on any canary, or the SHA-1 of one, found on disk, in the log, in the defaults or on the pasteboard, on a child left running, on a socket file under a run directory while the tour's engine is open or after the lock, on the door for the browser's file after the lock, on a host for Orion left running, answering a parent that is no browser or given anything after the lock, on a locked app that does not count the SSH agent with its switch on or counts it with it off, on `BW_SESSION` or a canary in what `ps eww` prints of a child while that engine is open, or on a seal file that holds its password unsealed, or on a passkey the tour could not sign with through the door, on a code it could not get through that door with the secret kept back, or on a locked app that does not count one timer with a pass standing, or still counts it after Revoke, or does not count the phone's door with a pass and a phone, or leaves its file behind. Five tests need the screen and skip behind a locked one, saying "the screen is locked" (`docs/notes.md`, "Building and signing"); a change that rests on one of them is not done on a run where it skipped. The canary's tour is on the real screen: a line that begins "canary: FOUND" is a leak, and one that says the tour "went wrong" is the tour, which a click in another app while Quick Access is up can cause ("quick access was put away while the vault opened under it"); read which before running it again. `make extension` zips `Extension/` to `build/OriPass-extension.zip`, for a browser that will not take the `.appex`. `make install` is the Release build, signed by hand with Developer ID in `$TMPDIR`, held to every check in `scripts/release.sh`, notarized under the profile `OP_NOTARY_PROFILE` names, stapled, and only then copied over `/Applications/OriPass.app` and started; with no profile it stops before it builds. `make release` stops before Apple and the copy, and `make canary-installed` is the canary over the installed app. `OP_APP_PROFILE` and `OP_AUTOFILL_PROFILE`, the paths of the two Developer ID provisioning profiles, put the system's AutoFill in either build; with neither it is left out, and with one the script stops before it builds. `make run` builds and launches; `OP_DEMO=1 make run` puts the demo vault behind the lock screen, password `demo`. `make shots` renders every surface to `shots/` four times, light and dark at each density. `make contrast` prints how far every word stands out from its ground and fails on one under 4.5 to 1; `ContrastTests` holds the same inside `make test`. Tests never touch the network, the real `bw`, the real vault, the real pasteboard or `~/Library`: `AppDelegate` returns early under XCTest, and everything else takes the fake backend, the fixtures under `Tests/Fixtures/`, temp directories and its own `UserDefaults` suite.

## Map

A change that adds a folder adds its line here in the same commit.

- `Sources/App/` `Main`, `AppDelegate`, `AppInfo`, `AppPaths`, `Log`, `Demo`, and `Instruments`, the registry of what keeps the app awake, which a test and the canary read by name to show that a locked app has no timer and one listener, the hot keys, which it keeps on purpose, and a second, the SSH agent, with its switch on, and with a pass standing the one timer it may have. `ScrollTrace` is `OP_DEMO=scroll`: two thousand invented items scrolled for ten seconds in a window on screen, and a count of the frames the main thread was late for. `QuickTrace` is `OP_DEMO=quick`: Quick Access shown and put away ten times, and how long each took to reach the screen. `TypeTrace` is `OP_DEMO=type`: a word put into Quick Access a letter at a time over two thousand items, and how long the main thread was at each.
- `Sources/Vault/` what an item is: `Item` and its payloads, `JSONValue` (the object as it came, which `Item.patched` sends back), `Redacted`. `VaultBackend`, the one protocol the engine stands behind, with `FakeBackend` and `DemoVault` on its near side. `SecretBytes`, a password that can be overwritten with zeros. `VaultStore`, the one place the open vault is held and the only thing a view reads; `VaultStore.said(ofAPassword:)` is where the engine's sentence for a wrong master password becomes this app's own, for the lock screen and the card that asks again. `Vault`, a row under VAULTS (Personal, a folder or a `SharedCollection`) and the order they are drawn in. `SignInEngine`, the second protocol, for the conversation that puts an account here, with `FakeSignIn`. `Login.word(forUsername:)`, in `Item`, is the one place a login's username is called "email" or "username", from its value; the details' row, the form's label, a linked field, Quick Access's copy and the key sheet's ⌘C all ask it, and nothing is stored for it. `Blank` is `Item.blank`, an item nobody has saved: the engine's two templates for its type with every example taken out of them, which is what a new item's form is filled from.
- `Sources/Bw/` the engine that is `bw`: `BwBinary` finds it, `BwChild` starts `bw serve` holding one end of a socketpair as descriptor 3, with no shell around it, so that nothing else can connect to it and it cannot outlive the app, `ServeConnection` is the app's end of that pair, a request at a time and of no more use after one that was not answered whole, and `ServeClient` is HTTP over it, knowing the envelope and nothing of the vault, with `ServeClient.host`, the one Host `bw serve` answers to. An answer that is no envelope under a failing status is `VaultError.turnedAway`, which the lock screen says with its status. `ServeBackend` is the two of them behind `VaultBackend`, and its `clearLeftovers` is what the delegate calls at launch over the real vault: `BwChild.clearLeftovers`, which kills a `bw` the last run left by the pid in `child.pid`, a file `stop` keeps for a child it could not see go. `BwVersion` is what `bw --version` says and the months the fixtures were recorded on (`written`); outside them the Account room says so under the version and nothing is blocked. A key `ServeBackend` needs and does not find is a `ShapeError` naming the route, which the store locks with. `LoginChild` is the one `bw` that may ask a question, `bw login` behind a shell that kills it when the app lets go, and `BwSignIn` is it behind `SignInEngine`, with `LoginTranscript` reading the CLI's sentences. `ServeBackend.signOut` is `bw logout` and then the folder `bw` keeps its state in emptied, which `VaultStore.signOut` and `Door.signOut` stand over: the seal first, and after it `VaultStore.didSignOut`, at which whatever else was the account's goes.
- `Sources/Lock/` `LockScreen`, what the window shows while the vault is shut, and `Door`, which swaps it for the panes and is where a password the engine took is sealed and where a finger unseals it to open the vault again. `EnclaveSeal`, a few bytes sealed to an enclave key that answers to a finger; `Enclave`, the protocol `TouchIDEnclave` and `FakeEnclave` stand behind; `PasswordSeal`, the master password in two files under `seal/`, its fourteen days, the mark of the fingerprints it was sealed under, bound into the box with the date, and the two older forms of seal, a session's and a password's that bound the date alone, which it deletes unopened; `FingerOffer`, the question asked once. `LockScreen`, what the window shows whenever the vault is not open, drawn from values and reading no store. `PasswordField` is its `NSSecureTextField`, and `SecureInput` is on only while that field has the keys. `LockPolicy` shuts the vault by itself on sleep, screen lock, saver, user switch, quit and ten idle minutes, each of them a switch in `LockChoices` that it follows as it is thrown, and exists only while the store is unlocked; `LockCommands` is the Vault menu with Lock on ⇧⌘L and Lock and Forget. `Door` decides which of the two the window holds, and takes Return to the store with a signpost around it. It makes `Panes` when the store unlocks and drops it when it locks. `Reprompt` asks again for an item with `reprompt` set, once for each item in each unlock, before a reveal, a copy, an edit, a fill or Large Type; the door owns the one the app has, and Quick Access and every window's panes go through it (`Panes.guarded`). `Authoriser` is who it asks: `OwnerCheck`, a finger while the password is sealed, which unseals it and wipes it unread, and otherwise the master password, typed into `PasswordCard` in a `PasswordPanel` and judged by the engine (`VaultStore.confirm`), or `FakeAuthoriser` in a test. `SignIn` is the sign-in sheet's model, the only holder of the master password between the form and the unlock, and `SignInSheet` draws it over the logged-out lock screen.
- `Sources/Window/` the unlocked window. `MainWindow` makes the one window, for the delegate and for a shot alike: no title, an empty `NSToolbar` that brings the traffic lights down, no restoration, and a frame remembered only when the delegate names it. `Panes` is its model, alive only while the store is unlocked. `PaneLayout` shares a width between the three columns and folds the sidebar when they do not fit; `PanesView` draws them, `SidebarView` is the first of them, `WindowToolbar` is the strip over the list and the details, and `WindowCommands` is ⇧⌘D, ⌥⌘F, ⌘1 and ⌘2 to ⌘9 in the View menu. The selected row and the VAULTS fold are on `Panes`, not in the sidebar, which leaves the tree when it is folded away. `History` is where the window has been, a row and an item at a time, behind ⌘[, ⌘] and the toolbar's chevrons; it is the panes' and goes with them. `ItemList` is one sidebar row's entries narrowed to a category and a filter, sorted and under their headings, with a row's grey line in `Item.secondLine`; `Panes.list` arranges it once per change and holds the selected item, the order and the category. `ItemListView` draws it in a lazy stack, each row's icon an `ItemIcon` (the site's, a lettered tile or a category's mark), with the header, the two menus the app draws itself (`ListMenuCard`), `ListKeys`, the AppKit view that takes the arrows and typed letters, and `ListStart`, the one that brings the list to the selected row when it is first drawn or put in another order. `ItemWindows` is the windows of one item each (⌘O), every one with panes of its own pinned to its item (`Panes.pinned`); `Panes.end` closes them, so the lock does. `VaultSheet` is the card that asks for a vault's name, the question before one is deleted, and `Panes`' side of both (`naming`, `deletingVault`); the sidebar's plus and a folder's right click raise them, and `VaultStore.makeVault`, `renameVault` and `deleteVault` are what they send.
- `Sources/Sync/` `SyncPolicy`, when the server is asked without Sync Now: a vault window becoming key five minutes after the last attempt, and a one-shot timer thirty minutes after it while such a window is on screen. It exists only while the store is unlocked, and the unlock's own sync stays in `VaultStore.load`. `VaultStore.sync` takes an item off the list only when two reads agree, and reads again when a change landed among them (`docs/notes.md`, "When a list comes back short"). `SyncStanding` is what the foot of the sidebar says, read from `VaultStore.standing` when the sidebar is drawn; `SyncFoot`, in `SidebarView`, draws it.
- `Sources/Icons/` a login's site icon. `SiteHost` is the one place an address becomes a host (and `Item.iconHost` its first address's). `IconStore` is memory, then `IconCache`'s files under Caches, then an `IconFetcher`, one request per host at a time and none for a row that has gone before its settle; the panes own it, and `Door` ends it as it drops them, so a lock cancels what it was asking and drops its memory. `BitwardenIcons` is the real fetcher and the only code that talks to the icon server, over one session that ends with the store and follows no redirect. `DemoIcons` draws the demo's icons, since a demo asks nobody.
- `Sources/Detail/` the third column with an item in it. `ItemDetail` is what is drawn for one item, worked out once per choice: the outlined group (each type's own: a login's, a card's with its number ending in its last four, an identity's, a key's, and for a type the app does not know every key of its payload, with a banner over it and Edit held off), the websites, the custom fields, the notes and the two dates, with no row for a value that is not there. `NoteText` reads the notes as Markdown into blocks and keeps a link only when a browser opens it. `ItemDetailView` draws them, a hidden value as ten dots that VoiceOver hears as "concealed". The chosen item's model, the open dates and where a link goes are on `Panes`. `Reading` is what is being done to the item in the details (revealed rows, the row under the pointer, its menu, "Copied", Large Type), held by `Panes` and emptied by `Panes.putAway` when another item is chosen; the `Panes` extension beside it is copy, reveal and the row's menu, and `Panes.end` is what the door calls before it drops the panes. `FieldMenu` is the menu a row drops, drawn by the app, `PasswordHistory` is the sheet its third entry raises over an item's earlier passwords (a copy held on `Reading`, so the lock and another item both take it), and `ItemCommands` is the Item menu: ⇧⌘C, ⌥⌘C, ⌘R, ⌘O and ⌘Delete, done to the item in the window that has the keys, with ⌘C arriving through `AppDelegate.copy`. `ItemMenu` is what the strip over the details drops: the item's menu behind the ellipsis and the vaults under the vault's name, the question before an item is deleted for good, the sentence the engine refused with, and a row dragged to the sidebar. Its `Panes` extension turns a row of the menu into an `ItemChange`, which `VaultStore.apply` makes with one call on the engine and then files among what it holds, reading no list again; `Item.copied` is the object a duplicate is made from. `ItemLayers` is everything laid over the details, worn by the main window and by a window of one item.
- `Sources/Keys/` every key the app answers to. `KeyTable` is the list: a `KeyCommand` for each row of `docs/look.md` "The keyboard", with its `Stroke`s, how it is bound and the card it waits for if it does nothing yet. The three menus make their items with `KeyTable.item`, `ListKeys` takes the bare keys in `PaneKey` and no others, and `KeySheet`, behind ⌘/, draws the rows that work. `PaneKeys` is what a bare key means in the column that has the keys (`Panes.focus`): the arrows, Return and Space, and the ring they leave. A new key is a row there first.
- `Sources/Editor/` the details as a form, for each of the five types and not for one the app does not know. `EditorForm` is every value as the text in its field, a login's, a card's, an identity's and a key's side by side with the ones that are another type's left empty, and `applied` turns it back into an item, taking from the form only the parts that no longer say what the item says. `Editor` is one item being changed: the item the form was filled from, the form, its open menu, its revealed rows and the banner. It is on `Panes.editor`, made by ⌘E, dropped by a save, a cancel and `Panes.end`. The `Panes` extension beside it is begin, cancel, save and `leaveEdit`, which everything that would take the window to another item asks first. A save is `VaultStore.apply(.edit)`, which sends nothing when the store no longer holds the object the form was filled from, and sends the old password first in the history when the password changed. `EditorView` draws it, with `DiscardQuestion` in `ItemLayers`: a card's number and code are one field each that is dots unless the caret is in it. `PastedKey` is a private key as it was pasted, read as OpenSSH's file for the public key and the fingerprint that go back with it, and `Panes.pasteKey` is the only reader of a pasteboard, through `Clipboard.string`. `NewItem` is ⌘N: `NewItemChoice`, the sheet's field and its lit tile, and the `Panes` extension that raises it, asks the store for a blank item of the tile's type, opens the same `Editor` on it and on Save sends it through `VaultStore.create`. `NewItemSheet` draws the sheet. An `Editor` whose item has no id is a new item's.
- `Sources/Generator/` the generator, which generates nothing: every password is the child's `GET /generate` (D4). `GeneratorSettings` is the controls, their reach, the recipe they make and the one dictionary of them in the defaults. `Generator` is the card while it is up, holding the last password the engine made for the controls and its `Strength`, asking again when one moves and showing only the last answer asked for; `Panes.generator` holds it, for a form's password field or by itself, and `Panes.end` ends it at the lock. `GeneratorCard` draws it with a slider, a switch and a row of segments of its own, under the wand in `EditorView` (`FieldGeneratorLayer`) or over the dimmed window from Password Generator in the Item menu (`GeneratorLayer`).

- `Sources/Search/` `SearchIndex`, what a search reads instead of the items: titles, usernames, hosts, the names of custom fields and notes, folded so that İ, I, ı and i are one letter, and no hidden value and no field's value at all. `VaultStore.index` makes one off the main thread behind each revision and the lock drops it. What is typed into the toolbar's field is `Panes.query`, and while it holds a letter `Panes.list` is what the index found, under one heading that counts them (`ItemList.init(found:)`). ⌘F is in `WindowCommands`.
- `Sources/Strength/` how strong a password is. `Strength` is the five levels and their words, the only place they are written. `Guesswork` counts the guesses, zxcvbn's way over `Words`, nine hundred words of this repo's own, and is why the level is an estimate. `VaultStore.score` runs it off the main thread behind a load and a sync and keeps the level on the `Entry`.
- `Sources/PasswordHealth/` what Password Health counts. `Watch` is four lists of the store's entries: the logins that share a password, found by marks made under a key that lasts one count, the ones in the bottom two levels, the ones with an `http://` address, and the cards that have run out or will within two months. `VaultStore.count` makes one off the main thread behind each revision, once that revision's passwords have their levels, and the lock drops it. Nothing in the archive or the trash is on a list. `WatchCard` is one of those lists as a card, with its name and its sentence, and `Dashboard` is the page as values: the cards with their counts and the strength bar's segments, from `Watch.levels`. `DashboardView` draws it where the list and the details would be, while `Panes.showsDashboard`; `Panes.show(_:)` is a card's "Show Items", after which `Panes.watched` is the card whose items the list holds, under its name and in no category. `WatchDrawing`, in `Sources/Design/`, is each card's line drawing. `Banner` is what the top of an item's details says when the item is on a list: a line, and a button where there is something to do, the most serious first in `WatchCard.seriousFirst`, the one place that order is written. `BannerView` draws it, `Panes.banners` makes them for the selected item and `Panes.perform(banner:)` is the button. `Panes.banners` and `Panes.dashboard` are worked out once for each item and count and handed back until one moves, beside the details' model in `Panes`; "Use https" opens the form with the address already changed, and saves nothing.
- `Sources/TwoFactor/` which sites take a one-time code, off until switched on (D13). `TwoFactorList` is the keys of 2fa.directory's `v4/totp.json` and says whether a host is under one of them and whether a login there has no code. `TwoFactorCheck` is the store's: it loads the list once an unlock, from `TwoFactorCache`'s file under Caches if that is a week old or less, otherwise through a `TwoFactorSource`, in one request that a cancelled count leaves for the next, and `VaultStore.lock` ends it. `TwoFactorDirectory` is the real source and the only code that talks to 2fa.directory; `DemoTwoFactor` answers from memory for the demo, the tour and the shots. What it finds is `Watch.twoFactor`, the Inactive two-factor authentication card, which `VaultStore.cards` leaves out while the switch is off.
- `Sources/Breach/` whether a password has been seen in a breach, off until switched on (D13). `BreachMark` is a password's SHA-1 cut after its fifth character and `BreachRange` the lines the server sends for five, with the padded ones dropped. `Breaches` is the store's: asked behind each count, it sends each five once through a `BreachFetcher`, four a second, and keeps a yes or a no under a mark made with a key that lasts the unlock; `VaultStore.lock` ends it. `PwnedRange` is the real fetcher and the only code that talks to Have I Been Pwned. `DemoBreaches` answers from memory for the demo, the tour and the shots. What it finds is `Watch.vulnerable`, the Vulnerable Passwords card, which `VaultStore.cards` leaves out while the switch is off.
- `Sources/Totp/` a one-time code. `Totp` is the secret read once from the three forms `login.totp` takes and the code it makes at a moment it is handed, RFC 6238 over CryptoKit's HMAC; it keeps no time. `CodeRow` is the row in the details: `CodeFace` draws the digits, the ring and the seconds from values, and a `TimelineView` draws it again each second only while the window can be seen and the row is in view, as `Totp/code` in `Instruments`. `CodeRow.still` is the one moment a run of shots draws every code at. The code is a row like any other to `Panes.copy`, with ⌥⌘C on `Panes.copyCode`, and an item that asks draws dots in its place until it is answered for.
- `Sources/Clipboard/` `Clipboard`, the one way a value reaches a pasteboard and the one way one is read from it: marked concealed, kept on this Mac, and cleared after ninety seconds or at the lock if the change count is still the one it left. The door owns it. Without a pasteboard it writes nowhere, which is every test's and every shot's default.
- `Sources/LargeType/` `LargeType` is a value cut into numbered cells, `LargeTypeView` draws them, and `LargeTypePanel` is the panel over the screen behind `LargeTypeStage`, the protocol a test stands a `RememberingStage` behind.
- `Sources/QuickAccess/` the panel behind the hot key. `QuickPanel` is the window: no frame, non-activating, able to take the keys, over full-screen apps and on every Space; `QuickPlace` puts it across the screen the pointer is on, its top a third of the way down. `QuickAccess` is the model, made once at launch by the delegate over the door: `toggle` is what a hot key calls, `query` is what was typed, `rows` is what it lists for that (before a letter the logins `Suggestions` finds for `inFront`, the app the hot key found in front, under `headings`, and then the items in `Recents`; after one what `SearchIndex` finds), `opened` is one item's `QuickAction`s, and `press` is every key, which the panel offers it before the field or the menu bar sees one. A copy goes to the door's `Clipboard`, puts the item first in `Recents` and closes the panel; Esc on an empty field, a click outside, the keys leaving and `VaultStore.didLock` close it and empty it too. A `QuickAccess` that is not the app's own is ended with `end`, since the panel and its view hold each other: a test's in `tearDown`, a shot's as it is built.
- `Sources/Front/` what he is looking at, and the logins for it. `FrontApp` is the app in front when the hot key fires, with `FrontApp.behindTheSheet`, the app the system's sheet is up over, and `Browser` the three whose tab can be asked for its address, each in its own dictionary's words, with `Browser.known`, every browser's bundle id, since a browser is suggested for by its page or not at all; `TabAsker` is who is asked, `AppleEventTabs` the real one, off the main thread, and the only code that sends an Apple Event. `PublicSuffix` reads the list under `Vendor/psl` and says which part of a host is the site, in either spelling of a name that is not ASCII, and names no site when it has no list. `Address` is an address read for its host, port and site, and `URIMatch.holds` is Bitwarden's six rules over two of them. `Suggestions` is the logins for a page or for an app, by its name and, when it is called after its maker's site, by its bundle id, from `Suggestions.Login`, which `SearchIndex` makes off the main thread with each revision. `Automation` says how each of the three stands in the system's Automation list without putting its question, `SystemAutomation` the real one and `FakeAutomation` a test's.
- `Sources/Fill/` a login typed into another app (D17). `Typist` waits for the app `QuickAccess.inFront` recorded to be in front with no modifier held, then sends the username, a Tab and the password a character to a key, or the password alone when the caret is in a secure field, and looks at what is in front before each one. It stands behind three protocols: `KeySink` (`EventKeys`, the only code that posts a key, to one pid), `Foreground` (`SystemForeground`: who is in front, what is held, where the caret is) and `Accessibility` (`SystemAccessibility`, the only code that asks macOS for the grant), with `FakeSink`, `FakeForeground` and `FakeAccessibility` for a test, a shot and the tour. `ArmedFill` is Open & Fill: ⇧⌘F and ⌥Return hand a login's first address to the default browser (`SiteOpener`: `SystemSites`, `FakeSites`) and arm that login for two minutes, so that ⌘\ in that browser fills it once without the panel; the door holds it and the lock clears it. "Return after the password" is `FillChoices` in the settings, and whether the system was asked is `QuickAccess.askedKey`, a key of its own; `FillNotice` is what the panel says when it copied instead. ⇧Return, the "Fill in" row and ⌘\ come in through `QuickAccess.fill` and `autofill`, which go through `Reprompt` first and stop the typist at the lock.

## Rules the code does not state

- `bw` holds the vault (D4). This app derives no key, decrypts no cipher string, stores no token and makes no call to Bitwarden's API. Everything goes through `VaultBackend`.
- Nothing decrypted is written anywhere (D6): no cache, no search index on disk, no window restoration, no log line that carries a value. The two exceptions are the copy of an attachment under a preview, which lives in `OpenCopies` and nowhere else, and, only with `PrivacyChoices.passkeysInSystemList` switched on, a relying party, a username and a credential id for each passkey in the system's list of identities while the vault is open, which `PasskeyOffer` writes and the lock, a quit and a launch take out. Lock empties the store, kills the child and destroys the panes; it does not hide them. What a lock leaves is a pass (D21, D22): every SSH key's private half in `AgentPass`, in memory and on no disk, wiped by every way it ends.
- No agent sees a real vault, its master password or a terminal it was typed into. An agent works against the demo vault and the fixtures. A check that needs a real account is run by hand, and what comes back from it is counts and timings, never a value. No file under version control is ever in the same pipe as the real vault.
- Views read `VaultStore` and never the backend. Its lists are computed once per `revision`, not per frame.
- A type that holds a secret conforms to `Redacted`, so `print`, `dump` and a failed assertion say its id and its type and nothing more.
- Only `Item.patched` builds JSON for a write, from the object the item was read from. An editor that rebuilt the object from the model would delete a passkey on the first save.
- A log line interpolates a count, an id or a state and nothing else.
- A two-step code or an emailed code reaches `bw` down a pipe. `--code` is an argument and is never used. What `bw login` writes on standard error repeats the code, and is never logged or shown.
- A master password is a `SecretBytes` from the moment the app has it, and is wiped by whoever is done with it. It never goes in a process's arguments, which every user on the Mac can read with `ps`, and it reaches the serving child down its connection and never through its environment. The app keeps no session: the one `bw` makes at an unlock is not read, and no child is started with `BW_SESSION` (D7). The one password still in an environment is `bw login`'s. A password a page took reaches the app only after a trusted click on the toast, as a `SecretBytes`; to ask whether the vault knows it, only a mark under a key made for that question crosses.
- The child's socket is one connected socket it is born holding, never a socket file and never TCP (D5). The run directory holds `child.pid` while a child lives and nothing else, and no test of the child makes a socket file. The three socket files the app makes are the door for the browser's, while the vault is open, the SSH agent's, while its switch is on, which no test makes at the real path, and the phone's, while a pass stands and a phone is registered or Add Phone waits, which a shut vault may have beside the agent's and no test makes at the real path either.
- Nothing in the name, the icon or any string says 1Password or Bitwarden, except where the app has to name the tool it needs.

## Signing

The team is never written in a tracked file. `Signing.xcconfig` reads `OP_TEAM` from `Team.xcconfig`, which git ignores, or from the environment; the entitlements name the group as `$(DEVELOPMENT_TEAM).oripass`, `scripts/release.sh` fills the team in before it signs, and the app reads its own team from its signature (`BridgeWire.team`). A bundle built inside a folder synced by iCloud Drive cannot be signed: Debug builds go to Xcode's DerivedData and the release builds to `$TMPDIR`.

## Commits

One change, one commit. Subject in the imperative, sentence case, no prefix, no trailer, naming what is different in the world and not the diff: `Start bw so that it cannot outlive the app`.  A body only when a choice could have gone the other way.
